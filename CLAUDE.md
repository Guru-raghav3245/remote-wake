Why: the user clarified the core goal is remote access to a Mac that is left PLUGGED IN with the lid closed; sleeping or not does not matter; battery is ignored; everything must stay free. ### Android app prototype (31 Oct 2026, emulator) — engine feasibility PROVEN in the emulator
Question: can a phone app embed the Tailscale engine (no VpnService, no root) and SSH into the Mac? Answer on the emulator: YES.
- `android-proto/main.go`: Go program (tsnet + golang.org/x/crypto/ssh, auth "none" because Tailscale SSH identifies by tailnet identity). Run on the Mac AND as a plain `GOOS=android GOARCH=arm64 CGO_ENABLED=0` executable in the emulator via adb: joined the tailnet and ran `id -un; hostname` on the Mac over SSH in 106 ms (Mac) and 187 ms (emulator). Login is a URL printed by tsnet that the user approves in a browser (or `TS_AUTHKEY`).
- `android-proto/engine/engine.go`: the same as a C-API shared library (`rw_start`, `rw_state`, `rw_exec`, `rw_free`), built with the NDK by `android-app/build-engine.sh` into `android-app/android/app/src/main/jniLibs/arm64-v8a/libtsengine.so` (22 MB, gitignored). Two fixes were needed to run INSIDE a real Android app (the adb-shell run hid both): (1) Android 11+ denies apps netlink, so `net.Interfaces` fails with `route ip+net: netlinkrib: permission denied`; fixed with `netmon.RegisterInterfaceGetter` returning a fake `lo` + `wlan0` (the same hook Tailscale's own Android app uses; one IPv4 address found by connecting a UDP socket, no IPv6); (2) no HOME/XDG_CACHE_HOME, Tailscale's log policy panics "no safe place found to store log state"; fixed by pointing both at the app's state dir.
- `android-app/`: Flutter app (Android only, package `com.guru.remote_wake_app`, flutter at `~/flutter`). `lib/engine.dart` = dart:ffi bridge (blocking Go calls run in `Isolate.run`), `lib/main.dart` = prototype screen: Tailscale state/IP, "Sign in to Tailscale" button, host/user/command fields, Run, output. Build: `./build-engine.sh` then `flutter build apk --debug --target-platform android-arm64`; install with `adb -s emulator-5554 install -r build/app/outputs/flutter-apk/app-debug.apk`. The app prints `AUTHURL <link>` to logcat (flutter tag) so a harness can open the login link on the Mac.
- RESULT in the emulator (arm64 google_apis_playstore android-35, AVD `rw_test`): app showed NeedsLogin, user approved the link, state Running (own tailnet IP), Run executed `id -un; hostname` on the Mac over Tailscale SSH in 116 ms, output `gururaghav` / `<mac-name>.local`. ### Reconnect on drop + Tailscale SSH "check" approval (2 Nov 2026, emulator) — built, committed
- Engine (`android-proto/engine/engine.go`): SSH keepalive every 5 s (a silent dead network is noticed in about 15 to 25 s), `rw_shell_dropped` (connection lost vs a typed `exit`, from `sess.Wait()`), 3-minute handshake deadline in `rw_shell_open` (was none), `rw_last_banner` (the server's SSH banner).

### Phone sessions (tmux) (4 Nov 2026) — BUILT, tested on the real Mac and phone
- Why: Claude Code (and other CLIs) keep their login in the macOS Keychain; an SSH login is not the desktop session, so on the phone they said "log in". `security unlock-keychain` failed for the user (keychain password differs from the login password; "Change Password for Keychain login" greyed out), so we avoid the keychain unlock. Fix: a tmux server started by the GUI app lives in the desktop (Aqua) session; phone logins attach to it and inherit the open keychain. Also keeps programs alive across a phone drop.
- Key fact: the server must be started with BARE `tmux -D` (child of the app). A normal start, or `-D start-server`/`-D new-session`, daemonizes into the Background session (`launchctl managername` = Background) and the keychain stays closed. Checked with `launchctl managername` inside the pane: Aqua.
- `app/build-tmux.sh`: builds tmux 3.8 + libevent 2.1.13 (static) from source, sha256-checked, arm64 only, into `app/vendor/tmux/` (gitignored, ISC licence file). Needs: no Homebrew on PATH (else it links /opt/homebrew libs), `--disable-utf8proc --disable-jemalloc`, `ac_cv_func_pipe2=no` (the SDK declares pipe2 as macOS 27+). The script fails if the binary links Homebrew or needs pipe2. `build.sh` bundles it to `Resources/tmux/`.
- `app/RemoteWakeMenu.swift` (top, "Phone sessions"): `setPhone(on)` copies tmux + `tmux.conf` to `~/Library/Application Support/Remote Wake/`, adds a marked block to `~/.zshrc` (attaches only when `SSH_CONNECTION` is set, not already in tmux, and session `phone` exists on socket `-L remotewake`; `&& exit`), starts the server. Off removes the block and kills the server. State = the block exists in `.zshrc` (works across the main app and the helper). The HELPER restarts the server at login or if it died (checked in `refresh()` every 5 s). New session starts in the home folder (`-c`). Windows/menu: "Phone sessions" card/row with a switch, shown only if the bundle contains tmux. Status line is short (`[phone] 0:zsh*`) so it fits a phone.
- zsh only (macOS default); bash users not covered. The block is also applied to any SSH login, not only the phone.
- TEST (real Mac + Nothing phone): switched on in the app, phone terminal landed in `[phone]` automatically, `claude` started and showed its folder-trust screen with NO login prompt. Killing the server made the helper recreate it within about 12 s.
- Android bug found and fixed: xterm 4.0.0 crashed on `CSI 1 K` (erase to cursor) at column 0 (`RangeError ... -1` in `BufferLine.eraseRange`), which killed screen updates when tmux/Claude drew. Fix: vendored patched copy `android-app/third_party/xterm` (MIT; `pubspec.yaml` path dependency; patch marked "remote-wake patch") plus a try/catch around `term.write`.
